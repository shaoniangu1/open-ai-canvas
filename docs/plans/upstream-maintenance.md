## 2. 目标配置

| 名称 | 职责 |
| --- | --- |
| `upstream` | 官方仓库，只获取上游历史；不作为日常推送目标 |
| `origin` | 用户自己的 fork，保存定制代码和自己的发布记录 |
| 自己的 `main` | 已验证的定制版本；接收经过审查的功能或升级分支 |
| `codex/<功能>` | 一项独立功能或修复，验证后合并 |
| `codex/upstream-<版本或短提交>` | 基于自己的 `main`，合并选定的官方提交并完成升级验收 |

官方代码基线由 `upstream/main` 和选定的 tag/commit 表示，无需再维护一条手工同步的本地“官方 main”。共享定制分支保留 merge 历史；不要反复 rebase 或强制同步 fork 来覆盖定制提交。

建议自己的 `main` 通过 PR 合并，要求相关质量检查通过，禁止强制推送和删除。GitHub 侧规则、访问权限和 Actions 是否启用须在自己的仓库配置，本轮未执行。

## 3. 一次性远程调整步骤

以下为首次配置参考。本地远程配置本轮已完成，勿重复执行重命名和添加命令。fork 地址由用户提供；GitHub 侧的可见性、保护规则和 Actions 设置未在本轮检查或更改。

1. 核对现有未提交文件，确认当前没有进行中的 merge/rebase。不要替其他会话提交、stash 或清理文件。
2. 将当前官方 `origin` 重命名为 `upstream`。
3. 把用户确认的 fork 添加为新的 `origin`。
4. 获取两个远程，核对自己的 `origin/main` 与本地 `main` 的差异。
5. 只有确认自己的 `origin/main` 存在且基线正确后，才调整本地 `main` 的跟踪关系。

示意命令如下；第二行中的地址必须先替换为已确认的真实 fork 地址：

```powershell
git remote rename origin upstream
git remote add origin '<已确认的 fork Git 地址>'
git fetch origin
git fetch upstream
git log --oneline --left-right main...origin/main
git branch --set-upstream-to=origin/main main
git config branch.main.pushRemote origin
```

上述操作不需要重置工作区。若本地与 fork 已经分叉，先说明差异并决定如何合并，不执行 `reset --hard`。远程重命名后直到跟踪关系调整完成前，本地分支可能仍跟踪官方；始终显式核对推送目标。

## 4. 定制代码的组织

- 按业务模块分离自有代码，沿用上游已有目录和职责。不要复制整份上游页面到另一套目录长期平行维护。
- 优先通过官方现有配置和官方插件配置完成定制，按下述顺序核对；只有确认当前能力不足，才采用自有插件或最小源码修改。
- 上游文件的改动集中在必要入口、注册和适配边界。通用修复与产品定制分别提交；只有用户授权后才向官方提交 PR。
- 一个提交表达一个目的，避免把上游合并、批量格式化和多个产品功能压在一起。不得手改锁文件以掩盖依赖冲突。
- 数据库迁移沿用上游现有机制，保持已应用迁移可追溯；每次升级检查迁移顺序、身份冲突和旧数据兼容性。

### 每项需求的处理顺序

| 优先级 | 先检查什么 | 满足需求时如何处理 |
| --- | --- | --- |
| 1 | 当前版本已有的后台设置、品牌／页面配置、官方插件及其参数 | 使用现成配置，记录操作入口、插件版本、非敏感配置和验证结果，不修改业务源码 |
| 2 | 当前已实现的插件注册、加载、界面入口、数据和业务操作接口 | 在现有接口范围内编写自有插件；明确是独立安装包还是需要随源码构建的内置插件 |
| 3 | 前两层无法覆盖的具体能力 | 只修改必要的宿主入口或新增独立业务模块，逐项说明改动文件、理由、验证和后续升级成本 |

“尚未核对”不等于“不支持”。以当前选定版本的实际实现为准，不能因为看到插件清单字段、接口类型、路线图或示例，就宣称已经可以上传即用。必要时在获准的隔离环境验证启停、权限、持久化和真实调用路径；不为了调查而自行安装插件、修改运行配置或发起付费调用。

如果满足完整需求必须重建插件运行时或大量绕过接口，应报告插件方案的实际成本，再比较有限源码改动；不要为了“全部插件化”增加更大的维护负担。通用缺口可列为上游改进候选，实际提交仍需授权。

### 从需求到交付

1. **明确结果**：写出用户要完成的操作、使用场景和验收标准，不先锁定实现技术。
2. **核对原生能力**：按上表检查官方配置、插件配置和已实现的扩展接口，给出版本与相关页面、源码或实际验证证据。
3. **说明最小方案**：列出可直接配置的部分、需要新增的部分及其维护成本。说明是否要改宿主、是否需要重新构建、是否涉及迁移。未验证项单列，不把设计写成已有功能。
4. **按授权实施**：分析或方案请求保持只读；用户明确要求实施后，在授权范围内处理常规细节，不重复索取同一授权。数据库迁移、付费调用、部署、发布等执行边界沿用根规范。
5. **隔离改动**：需要源码修改时开功能分支，保持既有工作区改动；按业务目的提交，不混入上游升级或无关格式化。纯配置任务不为走流程制造源码改动或空提交。
6. **验证用户行为**：配置能保存不等于生效，插件能安装不等于功能可用。按实际变更核对入口、业务结果、账号隔离、必要失败路径和持久化；金额或任务状态变化还要覆盖重复请求与恢复。只运行相关且必要的检查。
7. **记录并交付**：更新定制清单，说明实际改变、测试结果、未验证范围和恢复方法。以后合并上游时，依据清单检查定制仍有效；官方已有等效实现时评估移除自有补丁。

## 5. 官方更新流程

1. **选择目标**：阅读官方 Release/提交及迁移说明，记录要合并的不可变提交；不要未经评估直接追随 `main`。
2. **隔离升级**：在干净、已提交的定制基线创建升级分支。共享工作区有未提交内容时保留原工作区，待所有者处理或在明确安排的独立 worktree 中升级。
3. **执行合并**：将选定官方提交 merge 到升级分支。逐文件解决冲突，并核对注册入口、API、数据库迁移、插件和发布脚本。
4. **验证差异**：以升级前的定制提交为基准检查变化，执行相关测试、构建及定制验收。上游测试成功不能代替自有扩展的行为验收。
5. **审查合入**：将完整升级结果合入自己的 `main`，记录官方基线、定制提交和验证结果。升级工作中不重新计算成“已经没有差异”而跳过验证。
6. **单独发布**：发布获得授权后，构建自有镜像，在测试环境验证，再按发布计划推广；不因 merge 完成就自动切生产。

升级记录至少包括：旧定制提交、目标官方提交、合并结果提交、冲突处理理由、迁移影响、定制清单验收、失败及未验证项。

### 验证命令与基准

现有 `scripts/verify-before-push.mjs` 支持 `--base`，默认是 `origin/main`。首次重命名远程前，该默认值仍表示官方分支。更新后也要先核对引用是否已获取，避免与错误基线比较。

```powershell
# 独立功能分支：已确认 origin 为自己的 fork，且 origin/main 已获取。
bun scripts/verify-before-push.mjs --base origin/main

# 上游升级：替换为升级开始前记录的定制提交，而非已升级后的 HEAD。
bun scripts/verify-before-push.mjs --base '<升级前的定制提交 SHA>' --all
```

脚本当前会输出“落后时先 rebase”的上游提示；本 fork 的共享历史按根规范使用 merge 对齐，再重新验证，不机械照做 rebase。脚本不只是读取状态，会产生验证缓存；只在实际验证任务执行。

最小验收范围按变更选择：

| 影响范围 | 验证要求 |
| --- | --- |
| 纯文档 | 差异、链接路径、规则一致性；无需业务全量测试 |
| Web | 相应专项测试、类型检查；UI 改动检查真实页面；交付构建按上游要求执行 |
| Go 后端 | 相关包测试；公共行为、数据库和任务状态变化扩大范围 |
| 上游整版升级 | 运行现有检查脚本并核对覆盖；对登录、画布保存、素材引用、任务恢复、计费和自有扩展做相应验收 |
| PostgreSQL／Redis 路径 | 使用隔离环境覆盖；本地 SQLite 通过不能替代这些路径的结果 |

不得为验证擅自发起真实付费调用、付款、充值或使用生产业务数据。需要真实环境或付费验收时，单独列明范围及授权需求。
